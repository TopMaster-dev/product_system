「低在庫」の基準はSKUごとに変わります

以前は全商品いちりつに「9個以下」でしたが、Phase 2 からはその商品が実際にどれだけ売れているかから基準を決めています。

  • 考え方は「あと2週間もつ量を下回ったら低在庫」です。1日1個売れる商品なら14個、1日10個売れる商品なら140個が基準になります。
  • 基準の下限は3、上限は200です。ほとんど動かない商品が「在庫1でも正常」になったり、瞬間的に売れた商品の基準が跳ね上がったりしないようにするためです。
  • 基準は毎時の自動集計で更新されます。販売実績が変われば基準も変わります。
{{ note('同じ在庫数でも、商品によって ' ~ pill('low','低在庫') ~ ' になったりならなかったりします。異常ではありません。') }}
{{ head('1', 'ダッシュボード') }}

トップ画面です。カードをクリックすると各画面へ移動します。

  • 未解決アラート（赤）: 対応表が無くて止まっている注文の件数。0 以外なら対応が必要です。
  • 同期エラー（要対応）（赤）: 在庫反映に失敗した件数。0 以外なら「同期エラー」画面で確認します。
  • 承認待ちの照合（黄）: リコンサイルで承認待ちの件数。0 以外なら「リコンサイル」画面で確認します。
{{ note('毎日の確認ポイント: この3つが 0 になっていれば、基本的に運用は正常です。') }}
{{ head('2', '在庫一覧') }}

SKUごとの現在の在庫数を確認します。

{{ sub('検索・絞り込み') }}
  • 検索ボックスに SKUコード または 商品名 の一部を入れて {{ ui('検索') }}。
  • 「在庫状態」で すべて / マイナス / ゼロ / 低在庫 / 正常 / 売れ筋 に絞り込めます。
  • 画面上部の件数バッジは、クリックするとその状態だけに絞り込めます。
{{ sub('表示・並び替え・出力') }}
  • 初期表示は問題のあるSKUが上（マイナス→ゼロ→低在庫→正常）に並びます。
  • 列の見出しをクリックすると並び替えできます。
  • 右上の {{ ui('CSV出力') }} で、いま表示している条件のまま一覧をダウンロードできます。
  • 直近の販売が多いSKUには {{ ui('売れ筋') }} バッジが付きます。売れ筋かつ在庫が少ない場合は警告が出ます。
  • 各行の {{ ui('履歴 →') }} から、その SKU の在庫の動きを確認できます。
{{ note('ここでは在庫数の確認のみです。数を変えるときは「手動調整」「リコンサイル」「棚卸」を使います。') }}
{{ head('3', '分析 — 概要 / 売上明細') }}

売上と在庫の推移を期間で見る画面です。

{{ sub('期間の選び方') }}
  • 7日 / 30日 / 90日などのボタン、または日付を指定して表示します。
  • 「前期間比」は、同じ長さの直前の期間と比べた増減です。30日表示なら、その前の30日と比べています。
{{ sub('数字の読み方（重要）') }}
  • 売上・販売点数・受注件数は「期間の合計」です。日ごとの数字を足したものです。
  • 在庫数は「期間の最終日の数字」です。合計ではありません。「28日間ずっと5,000個」は140,000個ではなく5,000個です。
  • 受注件数は注文の数です。1つの注文に商品が3点入っていても1件と数えます。
  • キャンセル・返品は売上に含みません。
  • 回転率は「その期間での回転」です。年換算していません。7日間の回転率と90日間の回転率は、そのまま比べられません。
{{ sub('未マッピング売上') }}

商品を特定できていない売上です。売上金額には含めず、別枠で表示しています。金額が大きいときは画面に注意表示が出ます。「アラート」画面でSKUを対応づけると、正しい商品の売上に移ります。

{{ warn('データの蓄積開始日より前の期間を選ぶと、数字は少なく出ます。画面には集計できた日数が表示されるので、期間の日数と食い違っていないか確認してください。') }}
{{ head('4', '分析 — カテゴリ別') }}

リング・ネックレスといった分類ごとの売上を見ます。分類は「設定 → カテゴリ」で登録したものです。

  • 分類が設定されていない商品は 「未分類」としてまとめて表示されます。黙って除外はしません。除外すると各分類の合計と全体の合計が合わなくなるためです。
  • 大分類の数字には、その下の中分類の売上も含まれます。
{{ note('「未分類」が多いときは、設定 → カテゴリ で分類を登録してください。分類を変えると、過去の集計にもさかのぼって反映されます。') }}
{{ head('5', '分析 — 欠品リスク') }}

「このままだと、いつ在庫が尽きるか」を販売実績から見積もる画面です。補充の優先順位を決めるために使います。

{{ sub('列の意味') }}
  • 販売速度: 1日あたり何個売れているか。実際に動きのあった日数で割っています（売れなかった日を分母に入れると、たまにしか売れない商品の速度が実態より遅く出るためです）。
  • 残日数: 現在の在庫を販売速度で割った日数。
  • 欠品予測日: 残日数から計算した、在庫が尽きる見込みの日付。
{{ sub('「データ不足」「予測不可」と出たとき') }}
  • データ不足: 実績の日数が足りず、速度の信頼度が低い状態です。数字は参考程度に見てください。
  • 予測不可: 期間中に1個も売れていない、または在庫が0の商品です。計算できないことを、無理に数字にしていません。「予測不可」は異常ではありません。
{{ note('欠品予測はあくまで実績からの見積もりです。セールや新商品の投入など、これからの予定は織り込まれていません。') }}
{{ head('6', 'リコンサイル（在庫の突き合わせ）／ 在庫CSV取込') }}

外部の在庫CSVとシステムの在庫を突き合わせ、ズレ（差分）を承認して補正します。

アップロード→ 内容の確認→ 差分を承認→ 確定
  • 取込の時点では在庫は変わりません。承認した差分だけが在庫に反映されます。
  • 承認しなかった差分は「見送り」として記録に残ります。
  • {{ ui('確定') }} を押すと、未承認の差分は見送り扱いになり、その回の照合は終了します。
{{ warn('差分が異常に多いときは、取り込んだCSVが正しいか先に確認してください。CSVの中身が間違っていると、そのまま在庫が書き換わります。') }}
{{ head('7', '棚卸（実地棚卸）') }}

実際に数えた在庫数をシステムに反映します。カテゴリごとに分けて、日を分けて実施できます。

{{ sub('7-1. カウントシートを用意する') }}

技術担当がカテゴリごとのCSVを出力してお渡しします。列は次のとおりです。

  • sku_code … SKUコード（変更しないでください）
  • counted_qty … 実際に数えた数を記入する欄。最初は空欄です
  • 商品名 / カテゴリ / システム在庫数 / 備考 … 人が見るための列です
{{ note('システム在庫数は照合用に印字されています。数える前にこの数字を見て、そのまま書き写さないでください。「確認」になってしまい、棚卸の意味がなくなります。') }} {{ sub('7-2. 取り込む') }}

{{ ui('棚卸') }} → {{ ui('カウントシートを取り込む') }} から、記入済みのCSVをアップロードします。

  • 棚卸実施日は「実際に数えた日」を入れてください。取込日ではありません。金曜に数えて月曜に取り込む場合は金曜の日付です。
  • 対象範囲のチェックは記録用です。ここでの選択が取込対象を絞るわけではありません。差分が無かったカテゴリは履歴に痕跡が残らないため、「どこまで数えたか」を後から辿れるようにするための項目です。
{{ sub('7-3. 覚えておいていただきたい3つのルール') }}
  • シートに無いSKUは変更されません。 リングだけ数えた日にネックレスの在庫がゼロになることはありません。分けて実施して問題ありません。
  • 実数欄が空欄の行も「未計数」として対象外です。数えられなかった商品は空欄のままにしてください。
  • 同じSKUが複数行にあるときは、最初の1行だけを採用し、合算はしません。 2人が同じ棚を数えた可能性があるため、画面に警告が出ます。合算すると在庫が倍になってしまいます。
{{ sub('7-4. 差分を承認する') }}

取り込んだ時点では在庫は変わりません。差分一覧でチェックを入れて {{ ui('選択を承認') }} を押すと、その商品だけが実数で上書きされます。誤って承認した場合も、履歴が残るので手動調整で戻せます。

{{ warn('「差分」はシステムと実数が食い違った商品の件数です。一致した商品は記録に残らないため、差分0でも「数えていない」わけではありません。どこまで数えたかは「対象範囲」欄で確認してください。') }}
{{ head('8', '同期エラー') }}

在庫を各チャネルへ反映する処理が失敗したものの一覧です。

  • 原因（通信エラー、商品が見つからない等）を確認し、{{ ui('再実行') }} します。
  • 何度も同じエラーが出る場合は、マッピングや商品側の設定に原因があることが多いです。
{{ head('9', 'アラート（未マッピング注文の解決）') }}

注文に含まれる商品コードが、システムのどの商品か分からなかったものの一覧です。

  • {{ ui('未対応') }} {{ ui('対応中') }} {{ ui('解決済') }} のタブで状況を切り替えられます。
  • 正しいSKUコードを選んで {{ ui('解決') }} すると、対応表が作られ、止まっていた注文明細に反映されます。
  • 1つの注文に未知の商品が複数ある場合、1件解決してもその注文は保留のまま残ります。残りも解決すると確定になります。
{{ warn('商品コードが空欄のアラートは解決できません。空欄には複数の商品がまとまっているため、1つの商品に紐づけると他の商品の売上まで巻き込んでしまいます。表示された場合は技術担当へご連絡ください。') }}
{{ head('10', 'マッピング（SKU対応表）') }}

各チャネルの商品コードと、システムの商品を対応づける表です。

  • チャネル・商品コードで検索できます。
  • 新規登録・編集・無効化ができます。無効にした対応表は新しい注文には使われません。

カテゴリ（商品の分類）

カテゴリ別の売上分析に使う分類を登録します。

{{ sub('登録の手順') }}
  • まず大分類（リング、ネックレスなど）を作成します。
  • 必要に応じて、その下に中分類を追加します。
  • 各商品への割り当ては、画面から個別に設定するほか、CSVで一括設定できます。
{{ sub('CSV一括設定') }}
  • SKUコードとカテゴリコードの2列のCSVをアップロードします。
  • 取込前に内容を確認する画面が出ます。ここではまだ反映されていません。
  • 分類を変更すると、過去の集計にもさかのぼって反映されます。再集計は不要です。
{{ head('11', 'データ品質') }}

データの不備をまとめて確認する画面です。各カードをクリックすると、対応する画面へ移動します。

  • 要対応の項目: 未マッピング、マイナス在庫など、放置すると数字が合わなくなるものです。
  • 参考情報: アーカイブ済み、在庫管理対象外、親商品の件数など。対応不要で、現状を把握するためのものです。
  • 詳細検査: 在庫イベントの整合性（イベントの合計と現在庫が一致しているか）まで調べます。負荷が高いので、必要なときだけ実行してください。数秒かかります。
{{ sub('楽天SKU不備レポート') }}

楽天側の商品管理番号に不備があるものを一覧にしたものです。仮の番号のままになっている商品や、対応表が作れない商品が分かります。修正は楽天RMS側で行い、その後こちらで再取込します。CSVでダウンロードして、修正担当の方へお渡しできます。

{{ head('12', '手動調整') }}

在庫数を手で増やす・減らすことができます。

  • SKUを選び、増減する数と理由を入力します。理由はよく使うものがテンプレートとして選べます。
  • 確認画面で、調整前と調整後の在庫数を確認してから実行します。
  • 操作した人・理由・日時はすべて記録に残ります。
{{ warn('手動調整は在庫を直接変更します。棚卸で数を合わせる場合は「棚卸」画面を使うほうが、どの範囲をいつ数えたかが記録に残ります。') }}
{{ head('13', 'イベントログ') }}

在庫が動いたすべての履歴を検索できます（注文・キャンセル・手動調整・棚卸・入荷）。

  • SKU・種別・チャネル・期間で絞り込み。
  • 「なぜこの在庫数なのか」を後から追跡するときに使います。

覚えておきたい考え方

{{ sub('「在庫管理対象外」と「アーカイブ」は別のものです') }}
  • 在庫管理対象外は、ギフトバッグやクーポンのようにそもそも在庫を持たない商品です。注文が入っても在庫は減りません。在庫の分析からも外れます。以前これを設定していなかったため、ギフトバッグの在庫がマイナス12,509まで進んだことがあります。
  • アーカイブは、取り扱いを終えた商品です。今の在庫画面からは消えますが、過去の期間の売上集計には含まれます。除外すると、その商品が売れていた過去の売上が消えて、前期間との比較が壊れるためです。
{{ sub('セット商品・共有在庫は「売上は親、在庫は構成品」') }}

長さ違いで在庫を共有している商品や、セット商品では、売上は注文された商品（親）に計上し、在庫は共有している構成品から減らします。そのため「売上はあるのに、その商品の在庫が減っていない」ように見えることがあります。仕様であり、不具合ではありません。在庫は共有プール側で減っています。

{{ sub('数字が変わる操作') }}

次の操作をすると、過去にさかのぼって集計の数字が変わります。いずれもより正確になる方向の変化です。

  • アラートの解決 / マッピングの追加: 未マッピングだった売上が、正しい商品の売上に移ります。
  • カテゴリの変更: カテゴリ別の集計が変わります。
  • 過去の注文のキャンセル: その注文を受けた日の売上から差し引かれます。今日の売上からではありません。
{{ warn('マッピングをまとめて追加したときは、技術担当による再集計が必要になる場合があります。画面の数字が期待と違うときは、まずご連絡ください。') }}

補足（技術担当者向け）

  • 管理画面の認証は Basic 認証。内部ジョブのエンドポイントは Google 署名トークンで検証。
  • 楽天への在庫Pushは、対象カタログが「項目選択肢別在庫」方式のため別途対応（Shopify へは反映されます）。
  • 定期ジョブ: 楽天/Shopify ポーリング、バンドル在庫Push（毎時）、日次集計ロールアップ（毎時＋日次修復）、リコンサイル（毎朝 JST 06:00・承認待ちで作成）、BigQuery エクスポート。
  • 分析の数値は日次ロールアップ（daily_kpi_snapshots ほか）を読みます。受注データからの直接集計との突合は verify_analytics_totals で確認できます。
  • マッピングを一括追加した後は reresolve_order_items --rebuild-metrics。在庫は変更せず、売上の帰属のみを補正して該当期間を再集計します。
